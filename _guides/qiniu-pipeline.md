# 七牛云上传自动化：一次改动怎样才算真的生效

> 适用对象：需要把文件传上去、把链接发出去，并且经历过「我这儿是新的、对方那儿还是旧的」的人  
> 前置知识：同站的[《给静态网站加后端（无服务器函数）》](/guides/backend-serverless/)（密钥放哪、Worker 怎么部署）  
> 实验环境：个人免费账号、测试空间 `wyy-files`（华南-广东 `cn-south-1`、公开读）、七牛自动分配的 CDN 测试域名；下文所有响应头、ETag、字节数都是 2026-11-18 当天实测的原文  
> 成品：站内 `/tools/qiniu/`（页面）与仓库内 `_worker/qiniu/`（Cloudflare Worker，负责签凭证、调刷新、回读校验）  
> 更新日期：2026-11-18

事情的起点是一句话：「能不能做一个网页，贴个链接就把文件传上去，顺便把缓存刷了，像我们已有的 CI 那样。」

听起来是把控制台里的三次点击挪到网页上。真做下来会发现，难点根本不在网页，而在两件事：**凭证怎么发**，和**缓存怎么才算真的刷掉**。这篇按我实际走的顺序写：先手工把链路走通、把坑撞出来，再谈自动化。

## 1. 这件事的本质是四个动作

```text
① 签上传凭证  →  ② 把文件传上去  →  ③ 拼出外链  →  ④ 刷掉 CDN 缓存
```

前三个动作是「上传」类工具的标配，第四个才是这类需求真正的价值——也是唯一需要「管理凭证」的动作。四个动作里，**①④ 必须在服务端做**（它们要用密钥签名），②③ 可以完全放在浏览器里。

## 2. 三层模型：空间、key、域名

七牛的心智模型只有三层，记牢了后面都顺：

| 层 | 是什么 | 例子 |
| --- | --- | --- |
| 空间（Bucket） | 一个存储区域，带访问权限和区域 | `wyy-files`，华南-广东 `cn-south-1`，公开读 |
| key | 对象在空间里的名字，**就是完整文件名** | `test/v1.png` |
| 域名 | 访问入口，决定 URL 长什么样 | `toofb0znl.hn-bkt.clouddn.com` |

外链的拼法只有一种：

```text
<域名>/<key>
```

三个反直觉的地方：

1. **七牛没有目录。** `test/v1.png` 不是「test 目录里的 v1.png」，它就是一个名字里带斜杠的 key。控制台的「创建目录」只是按前缀筛，不是真的建了文件夹。
2. **key 包含扩展名，是逐字符比较的。** 覆盖时 `.jpg` 和 `.png` 是两个不同的对象——我第一次「同名覆盖」就是因为扩展名没改，结果传成了第二个文件，缓存实验直接作废。
3. **访问控制选公开还是私有，决定链接能不能直接用。** 私有空间每给一个链接都要签名，签名有有效期，不能当长期下载地址。公开空间才能把 URL 直接贴出去，代价是谁拿到 URL 谁都能下。

## 3. 凭证：两种，别混

七牛的密钥是一对 `AccessKey` / `SecretKey`，**账号密码级别的凭证**。它能签两种东西：

| 凭证 | 用途 | 有效期 | 给谁 |
| --- | --- | --- | --- |
| 上传凭证（uploadToken） | 授权某次上传，可限定到具体 key | 由策略里的 `deadline` 决定，可以只给几分钟 | 可以给浏览器 |
| 管理凭证（accessToken） | 调管理类接口，例如刷新缓存 | 请求级，每次现签 | 只给服务端 |

上传凭证不是密钥本身，而是「用密钥对这个上传策略做的签名」。策略里至少要有 `scope`（空间名，或 `空间名:key`）和 `deadline`。所以正确姿势是：

```text
浏览器  ──① 请求凭证──▶  服务端（拿 AK/SK 签一个几分钟有效的 token）
浏览器  ──② 带 token 直传──▶  七牛上传入口
浏览器  ──③ 拿到 key / hash──▶  自己的记录表
```

**文件字节永远不经过自己的服务器。** 这么切有三个好处：密钥不出后端；大文件不用自己中转，也不会撞上无服务器函数的请求体上限；上传失败重试不需要重走自己的服务。

绝对不要做的事：把 `AccessKey` / `SecretKey` 写进网页、写进前端能读到的配置、或者提交进 git。任何人拿到它，就能以你的名义往空间里写东西、刷你的流量。

## 4. 实测：一年缓存是怎么把人坑住的

### 4.1 第一次请求（缓存里什么都没有）

```text
HTTP/1.1 200 OK
Age: 0
Cache-Control: public, max-age=31536000
Content-Length: 178865
Content-Md5: OqBEDBjmE6q1ZDpBFiMP8A==
Etag: "FgK9KfzTj464AyznJnVtLLREgyhr"
X-Bdcdn-Cache-Status: TCP_MISS,TCP_MISS
X-Response-Cache: miss
```

`TCP_MISS` + `Age: 0` 说明这次是回源取的，缓存在写入。**真正要命的是 `max-age=31536000`——一年。**

### 4.2 第二次请求（43 秒后）

```text
Age: 43
X-Bdcdn-Cache-Status: TCP_MISS,TCP_HIT
X-Response-Cache: parent_hit
```

命中父层，连源站都没回。这份缓存的保质期是一年。

### 4.3 同名覆盖之后，用户拿到的还是旧文件

把 174.67 KB 的旧图换成 38.65 KB 的新图（同名覆盖），再请求：

```text
Age: 271
Content-Length: 178865
Content-Md5: OqBEDBjmE6q1ZDpBFiMP8A==
Etag: "FgK9KfzTj464AyznJnVtLLREgyhr"
Last-Modified: Wed, 18 Nov 2026 02:40:06 GMT
X-Bdcdn-Cache-Status: TCP_HIT
```

源头的文件已经是新的，对外发的还是四分钟前那份旧的，而且会这样发一年。**这就是「改了等于没改」的完整现场。**

### 4.4 控制台点一次「刷新 CDN 缓存」，再请求

```text
Age: 0
Content-Length: 39582
Content-Md5: PVCLky346MEo0QEluL0oLQ==
Etag: "Fu82PiMAx-BEWwMahp0J3Qg8fjpi"
Last-Modified: Wed, 18 Nov 2026 02:46:22 GMT
X-Bdcdn-Cache-Status: TCP_MISS,TCP_MISS
X-Response-Cache: miss
```

三条同时变了，才叫真的生效：**字节数**、**内容 MD5**、**Last-Modified**。

### 4.5 怎么判断「新版到底出没出去」

别靠肉眼，靠响应头：

| 看什么 | 怎么判 |
| --- | --- |
| `Content-Length` | 大小差得多时最好用，一眼看出新旧 |
| `Content-Md5` | 文件内容的 MD5，最硬的证据 |
| `Etag` / `Last-Modified` | 变了就是新对象，但别依赖 ETag 的算法细节 |
| `Age` / `X-Bdcdn-Cache-Status` / `X-Response-Cache` | 判断是缓存给的还是回源给的 |

七牛用的是融合 CDN，节点可能来自不同厂商（我那次 `Server` 是 `Byte-nginx`，字节的节点），所以缓存是**分层**的：边缘一层、父层一层、七牛回源代理一层。刷新是从里往外推的，**不是瞬时**的——从点击到全量生效留出 1～2 分钟是正常预期。

顺带一个可以放心依赖的细节：**CDN 响应头里的 `Etag` 和上传接口返回的 `hash` 是同一个值**，所以「校验新版本有没有生效」只需要比较这两个字符串，不用额外存哈希。

### 4.6 工具第一次跑通时的日志

```text
刷新任务已受理，requestId: 6afd1e88...
今日剩余刷新额度：495 / 500
第 1 次回读：HTTP 200，长度 45714（应 45714），etag Frq0oaFq...，缓存 TCP_MISS,TCP_MISS 内容已更新
刷新任务状态：processing（20%）
校验通过：对外已经是新文件。
```

注意这两个时间点：**回读在第 7 秒就已经拿到新内容，而七牛的任务状态还停在 20%**。

也就是说「任务状态」和「用户实际拿到什么」是两回事。做工具时如果只看任务状态，要么得多等几分钟，要么会在已经生效时误报失败；只看接口返回 200 就更糟——那只是「请求被受理」。

## 5. 坑清单

| 坑 | 后果 | 怎么办 |
| --- | --- | --- |
| 默认缓存一年 | 覆盖后一年内用户看不到新版 | 上传后主动刷新，或调低空间的缓存策略 |
| key 必须逐字符相同（含扩展名） | `.jpg` 覆盖不了 `.png`，会变成两个对象 | 覆盖前对一遍完整文件名 |
| 控制台文件列表的大小/时间列会滞后 | 以为没传成功，实际成功了 | 以「详情」页为准 |
| 测试域名只支持 HTTP，没有证书 | 浏览器标「不安全」，`curl` 报 `SEC_E_WRONG_PRINCIPAL` | 生产必须绑自定义域名并配证书 |
| 测试域名强制下载 | 点开是下载框，不能在线预览 | 同上，绑自定义域名 |
| 测试域名 30 天后回收 | 到期链接全失效 | 只用来验证机制，别放正式内容 |
| 测试域名禁止 apk / ipa / exe / dmg | 放安装包会被处理（官方说明是「不得使用测试域名存储、发布」） | 固件、安装包走正式域名 |
| 公开空间有流量盗刷风险 | 链接被转发后流量算你的钱 | 开 Referer 防盗链，或改私有 + 后端签名 |
| 刷新额度有限（500 次文件刷新/天，单次最多 20 个 URL） | 批量发布会撞上限 | 只刷真正改过的 key，批量任务要排队与提示；响应里的 `urlSurplusDay` 就是剩余额度 |
| 刷新不是瞬时 | 工具若刷完立刻报成功，用户会看到旧内容 | 刷新后回读校验，见第 6 节 |
| **密钥粘贴可能被替换字符** | 长度、首尾字符都正常，但签名永远是 `BadToken` | 比 `sha256(SK)` 的指纹，不要靠肉眼或长度判断 |
| 官网示例可能与最新文档矛盾 | 2018 年的 curl 示例看起来把请求体也签了进去 | 以 2026 版《鉴权指南》为准，实测见第 8 节 |

## 6. 自动化该怎么设计

把上面这些串成一条能用的流程：

```text
① 浏览器要凭证  →  服务端签 uploadToken（scope 限定到 key，deadline 只给几分钟）
② 浏览器直传    →  拿到 key 与 hash
③ 拼外链        →  <域名>/<key>
④ 调刷新接口    →  服务端用管理凭证签 accessToken
⑤ 回读校验      →  轮询外链，比对 Content-Length / Content-Md5，一致才算成功
⑥ 落一条记录    →  谁、什么时候、哪个 key、刷没刷成
```

第 ⑤ 步是这类工具最容易偷懒、也最该做的一步。**刷完就弹「成功」等于没做校验**：缓存分层 + 非瞬时生效，用户很可能正好撞在旧内容上，然后认定「你这个工具不靠谱」。

另外两条设计上的取舍：

- **「直接放链接」优先交给七牛自己抓。** 七牛有「异步第三方资源抓取」的接口，可以把源 URL 交给它去拉，省掉自己下载再中转的带宽和超时问题（这条还没实测，见第 9 节）。
- **批量任务必须能重试、能看历史。** 上传和刷新都会失败，失败原因要落到记录里，否则三天后没人查得清是谁传的、传到哪一步断的。

## 7. 上生产前必须补的

这三条不是优化，是前置条件：

1. **已备案的域名。** 七牛绑任何自定义域名都要求「提前将域名在工信部备案」，并且从 2022-06-08 起有备案巡检，异常会冻结域名。
2. **HTTPS 证书。** 测试域名不带证书；正式域名要自己配，否则浏览器直接标不安全。
3. **防盗链或私有读。** 公开空间的链接一旦被转发，流量就是你的账单。

至于「能不能直接拿测试域名当生产」——官方在弹窗里写得很直接：不得作为生产域名，使用期间不在 SLA 保障范围内。

## 8. 签名怎么验：别猜，比哈希

这套流程里唯一会「每一行都照文档写了，但就是不工作」的地方，是签名。我在这上面栽了两次，两次都不是算法写错。

### 8.1 QBox 只签路径，不签请求体

七牛 CDN 接口（`fusion.qiniuapi.com`）用 QBox 鉴权，签名串就是「接口路径 + 一个换行」，base64url 编码时**尾部 `=` 要保留**：

```text
/v2/tune/refresh\n
```

不带 method、不带 host、不带请求体。我把四种拼法各打了一次真接口：

| 拼法 | 结果 |
| --- | --- |
| `path + "\n"`，保留 `=` | **200** |
| 同上但去掉 `=` | 401 BadToken |
| `path + "\n" + json body` | 401 BadToken |
| `"POST " + path + "\n" + json body` | 401 BadToken |

**2026 版鉴权指南是对的，2018 年那个 curl 示例会把人带偏**——它看起来像把 body 也签进去了，照抄就 401。

### 8.2 密钥可能被替换字符，而长度和首尾都对

更阴的一次：`BadToken` 反复修不好，最后查出 AK 是对的、SK 不是——可那个 SK 长度 40、开头 `tf`、结尾 `4`，和真的完全一样。

定位办法不是把密钥打印出来看（那等于二次泄露），是**比指纹**：

```text
本地   sha256(SK) 前 12 位 = 91fd145caaf1
Worker sha256(SK) 前 12 位 = 9dbf73aa99ca     ← 不是同一个字符串
```

用控制台的「复制」按钮重新粘一次（不要用鼠标划选，划选容易带上隐藏字符），两边对上，`BadToken` 立刻消失。

**结论：排查凭证问题，比长度、比首尾字符都不够，要比哈希。**

## 9. 还剩下的

- 大文件的分片上传（v2）与断点续传；
- 「异步第三方资源抓取」能不能替代自己下载再中转；
- 刷新生效时间的分布（只测到一次 7 秒、一次 1～2 分钟，样本太少，谈不上统计）；
- 目录刷新（`dirs`）——官方说明里目录刷新额度只有 11 次/天，且需要单独开通。

## 10. 一句话总结

上传只是搬运，**刷新才是这个工具存在的理由**；而刷新的正确做法不是「调完接口就报成功」，是「调完接口去回读，确认用户真的拿到了新版本」。
